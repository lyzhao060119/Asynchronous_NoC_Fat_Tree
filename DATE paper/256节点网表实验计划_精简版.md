# 256 节点网表实验计划（精简版）

> 目标：256 节点不重复 64 节点已经完成或计划完成的机制消融、Async/Sync、BC/Hotspot、Router PPA 等实验。  
> 256 节点只承担三个紧凑任务：
>
> 1. **Scale-out：**验证从 64-node 单 tile 扩展到 4×64-node 后，Proposed topology 相对 FlatMesh256 的行为。
> 2. **Cross-tier Multicast：**验证 Native Multicast 真正跨越 local hierarchy → upper Mesh → remote tile 后仍然有效。
> 3. **Locality sensitivity：**验证 tile-local traffic 增加时，层次网络是否比 FlatMesh256 获得更大的延迟/拥塞改善。
>
> 64 节点负责：完整消融、Async/Sync、robustness、multicast fanout scaling、PPA/energy。  
> 256 节点负责：**multi-tile system validation**。
>
> **256 节点不做功耗 / 能量分析。**

# 3. 256-E1 — Global Uniform Random Scale-out

## 3.1 目的

回答：

> 当网络从 64 个节点扩展到 256 个节点、开始经过 upper Mesh 后，Proposed hierarchy 是否仍然能够保持更高的有效吞吐并延后 saturation？

## 3.2 DUT

### PROP-M16

- 4 × current PROP64 tiles
- common upper Mesh
- 当前正式 Proposed architecture

### FlatMesh256

- 16 × 16 conventional mesh

用途：

- external topology baseline

## 3.3 Benchmark

### Global Uniform Random

对于所有 256 个 source：

- destination 从其余 255 个 PE 中 uniform random；
- `destination != source`；
- 5 flits / packet；
- continuous-time injection；
- PROP-M16 / FlatMesh256 使用完全相同 canonical trace。

由于系统有 4 个 64-node tiles，Global UR 中约 75% 的目的节点天然位于其他 tile，因此已经会触发大量 upper-Mesh communication。

因此：

**不再额外做 Forced Inter-Tile UR。**

## 3.4 Load Sweep

完整扫描：

`low load → knee → saturation → slightly beyond saturation`

建议：

1. 先 coarse sweep；
2. 自动识别 knee；
3. knee 附近增加 fine load points；
4. paper-facing latency 只使用 pre-saturation / near-lossless 区域。

## 3.5 核心指标

必须统计：

- offered throughput
- delivered throughput
- delivery ratio
- mean latency
- p95 latency
- backlog
- peak delivered throughput
- near-lossless throughput
- saturation knee

推荐 near-lossless criterion：

- delivery ratio ≥ 99%
- backlog 很小且无持续增长
- correctness PASS

## 3.6 Correctness

正式性能统计前必须满足：

- `Total errors = 0`
- sent == received after full drain
- no missing flits
- no unexpected flits
- no timeout
- same input trace across DUTs

任何 configuration FAIL 时停止批量扫描，先修复。

**不做。**

如果 DC 自动产生可信 area，可以记录 area，但不需要专门做：

# 4. 256-E2 — Cross-tier Native Multicast

## 4.1 目的

64-node 已经证明 Native Multicast 对 high-fanout communication 有效。

256-node 必须进一步证明：

> 当 multicast destinations 跨越多个 64-node tiles，需要经过 local hierarchy → upper Mesh → remote hierarchy 时，Native Multicast 仍然有效。

这是 256 节点最重要的 multicast 实验。

## 4.2 DUT

只使用当前正式：

**PROP-M16**

比较：

- Native Multicast
- Source Repeated Unicast

不需要再引入 PFAT256 / FlatMesh256。

原因：

该实验主要验证 M2 的 cross-tier behavior，而不是重新做 topology comparison。

## 4.3 Benchmark

固定：

**Fanout = 16**

不再重复 64-node 的：

`F = 2 / 4 / 8 / 16 / 32`

fanout sweep。

## 4.4 Destination Distribution

每个 original multicast transaction 有 16 个 destination。

强制均匀分布到 4 个 tiles：

`4 + 4 + 4 + 4`

即：

- source tile：4 个 destinations
- 其他 3 个 tiles：各 4 个 destinations

从而每个 transaction 必然包含：

- local delivery
- remote delivery
- upper-Mesh traversal

destination 必须：

- 去重；
- 排除 source；
- Native / Repeated 使用完全相同 destination set。

## 4.5 Native vs Repeated 定义

### Native

`1 original transaction → 1 multicast packet`

网络内部按 routing / branching mechanism 复制。

### Repeated Unicast

`1 original transaction → 16 source-side unicast packets`

16 个 packet 对应完全相同的 16 个 destinations。

两者必须共享：

- same original arrival time
- same source
- same destination set
- same packet length
- same canonical trace

## 4.6 Load Points

为了节省 256-node GLS 时间，不做超密 load sweep。

先用少量 exploratory points 找到性能区域，然后冻结 3 个 paper-facing points：

### Point A — Low Load

要求：

- full drain
- zero backlog

用途：

- 比较 multicast completion latency

### Point B — Medium Load

用途：

- 比较 latency + useful throughput

### Point C — High but Pre-Saturation

用途：

- 比较 useful destination throughput
- backlog
- completion ratio

禁止使用已经严重 right-censored 的 latency 作为 headline。

## 4.7 核心指标

### Completion Latency

定义：

> 一个 original multicast transaction 的最后一个 intended destination 收到 Tail 时，该 transaction 才算完成。

统计：

- mean completion latency
- p95
- p99

### Useful Throughput

建议统计：

- completed original transactions / s / source-port
- useful destination deliveries / s / source-port

### Congestion

- backlog
- completion ratio
- timeout/errors

### Optional

如果 upper-Mesh interface 能直接观测真实 accepted flits，可记录：

- upper-Mesh accepted traffic
- per-plane traffic

但：

**route-oracle predicted link traversal 不得标成 measured traffic。**

Native vs Repeated

正文只需要强调：

- low-load completion latency

不需要再重复 64-node fanout-scaling 图。

## 4.9 功耗 / 能量

**不做。**

Multicast energy 的物理证据由 64-node F16 实验承担。

256 仅证明 cross-tier functional/performance scaling。

# 5. 256-E3 — Tile Locality Sensitivity

## 5.1 是否值得做

**值得做，但只能作为 locality sensitivity，而不能直接称为神经网络 workload。**

Global UR 中同 tile 概率本来就是 `63/255 ≈ 0.247`，它主要考察跨 tile 广度和 upper-Mesh 压力。实际神经网络映射通常会尽量把强通信关系放在邻近 PE，因此需要一个可控的 locality 参数，检查 hierarchy 是否能把局部通信留在 64-node tile 内。

FlatMesh256 在局部流量下也会因为 Manhattan distance 下降而受益。因此本实验真正回答的是：

> 随着 tile-local probability 增加，PROP-M16 相对 FlatMesh256 的延迟、尾延迟和拥塞改善是否更快？

如果两者改善幅度相同，不能声称 hierarchy 具有 locality advantage，只能报告两者都对 locality 敏感。

## 5.2 Traffic definition

对每个 source 和每个单播 packet：

- 以概率 `p` 从 source 所在 64-node tile 的其余 63 个 PE 中均匀选择 destination；
- 以概率 `1-p` 从其他三个 tile 的 192 个 PE 中均匀选择 destination；
- 始终满足 `destination != source`；
- source 在全部 256 个端口上均匀分布；
- header 继续使用独立指数间隔，body/tail ASAP 连续发送；
- 5 flits/packet、seed `202701`、1000 warmup + 10000 measurement originals；
- PROP-M16 与 FlatMesh256 使用完全相同 canonical trace 和 original event timing。

FlatMesh256 的四个“tile region”按与 PROP 相同的 node-ID 分组，对应四个连续 8×8 quadrant。这样 locality 定义对两个 DUT 完全一致。

## 5.3 Locality points and load

固定四个 locality 点：

`p ∈ {63/255, 0.50, 0.75, 0.90}`

- `63/255` 与 Global UR 的 destination 分布严格等价，是控制点；
- `0.50` 与 `0.75` 表示中等/强 locality；
- `0.90` 表示高 locality，但仍保留跨 tile 流量；
- 不使用 `p=1` 作为正文点，避免退化为完全隔离的四个子网。

只使用一个固定负载 `M_LOC`：修复后的 E1 中，PROP-M16 与 FlatMesh256 在 `p=63/255` 下共同满足 correctness PASS、delivery ratio ≥99% 和 backlog ≤5 的最高负载。不得按每个 `p` 分别挑选不同负载。

总规模为 `4 p × 2 DUT = 8` 个 MAXIMUM-SDF GLS case。若控制点不能通过 correctness gate，停止整个 locality 实验。

## 5.4 Metrics and mechanism evidence

正文报告：

- delivered throughput / port；
- full-drain flit mean、p95、p99 latency；
- measurement backlog；
- 相对 `p=63/255` 的 latency reduction；
- PROP-M16 相对 FlatMesh256 的 latency ratio/crossover。

机制证据优先使用 PROP-M16 upper-Mesh 边界的真实 accepted Req/Ack flit count，并报告其随 `p` 增加的下降趋势。不得用 route-oracle `link_traversals` 冒充实测链路活动。

## 5.5 Claim boundary and output

生成紧凑的 Fig.256-3：

- x-axis：tile-local probability `p`；
- panel (a)：mean/p95 flit latency；
- panel (b)：normalized latency improvement 与 PROP upper-Mesh accepted traffic。

只有在 matched trace、正确性通过且 PROP 的相对改善显著大于 FlatMesh 时，才可写：

> The hierarchy benefits from communication locality by retaining more traffic within a 64-node tile.

该实验仍是 synthetic locality sweep。若要声称“代表神经网络工作负载”，后续必须增加真实映射 trace；本实验本身只能说明 locality mechanism，不说明具体模型端到端性能。
